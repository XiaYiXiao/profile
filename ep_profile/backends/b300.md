# B300 环境的后端可选列表

更新日期：2026-11-03。对应 [当前 H20 环境](h20_current.md)。

## 适用范围与证据边界

本文假设将同一个 MiMo-V2.6-Flash-MOPD 模型（MXFP4 专家权重、SiLU、Q/K head dimension=192、V=128）迁移到 B300，并沿用 TP=2、DP=2 的实验设计。

B300 的 compute capability 是 **10.3（SM103）**，属于数据中心 Blackwell。它与 B200 的 SM100、消费级 Blackwell 的 SM120 不应混为一谈。[NVIDIA GPU 算力表](https://developer.nvidia.com/cuda/gpus)

以下结论基于当前 /host/vllm 工作区源码，HEAD 为 db3b0f0fae4bc98492b3863685e541e62bc59576。**本次没有访问或测试 B300 机器，全部 B300 可用项均为候选，不标为已实跑。** B300 的实际卡数、显存、NVLink/NVSwitch 拓扑、RDMA、驱动和软件依赖需要以目标机器为准，不能直接照搬 H20 的检测结果。

设备检查接受 SM103，只代表通过源码中的硬件门槛。还需核实安装包包含兼容 SM103 的 kernel 或可用的 JIT 编译路径；尤其不能假定仅含 sm_100a 的构建一定适用于 B300。NVIDIA 对架构专用代码有独立兼容性限制：[Blackwell 兼容指南](https://docs.nvidia.com/cuda/blackwell-compatibility-guide/index.html)。

## --moe-backend：专家计算

下表普通候选默认按 allgather_reducescatter 通信组合理解。

| 参数值 | B300 判断 | 对当前模型的含义及限制 |
|---|---|---|
| `auto` | 候选 | 当前通用 MXFP4 优先列表先尝试 FLASHINFER_TRTLLM_MXFP4_MXFP8，再尝试 DeepGEMM、Marlin、Humming 等；实际选择以兼容性检查和日志为准 |
| `flashinfer_trtllm` | 硬件门槛通过，待实测 | 支持 10.x；目标 FLASHINFER_TRTLLM_MXFP4_MXFP8 属于该后端族。CLI 名称覆盖 BF16/MXFP8 变体，单独指定族名不保证选中特定激活精度 |
| `deep_gemm` | 候选 | 当前 DeepGemmFP4Experts 接受 10.x，支持 MXFP4 权重、动态块 FP8 激活、SiLU；要求对应 DeepGEMM 安装和构建 |
| `flashinfer_cutlass` | 候选 | 当前代码在 10.x 上支持 MXFP4 权重 + MXFP8 激活；不要照搬 H20 的 MXFP4/BF16 结论 |
| `marlin` | 候选 | 设备和权重量化检查覆盖 B300；不支持 flashinfer_nvlink_two_sided |
| `humming` | 候选 | 设备检查覆盖 B300，但仍需对应 Humming kernel 构建和量化方案支持；不能套用 H20 上的优先级或性能结论 |
| `triton_unfused` | 实验性候选 | 源码覆盖 SM103、MXFP4、SiLU；因 MTP 问题被移出自动列表，需独立验证 |
| `triton` | 当前模型不适配 | MXFP4 专家实现要求 SWIGLUOAI；更换 GPU 不会消除 MiMo 的 SILU 不兼容问题 |
| `flashinfer_moe_ep_cutedsl` | 高度受限的 EP 候选 | 硬件白名单明确包含 SM103；要求 EP、特定权重和并行条件，内部负责通信，需要 passthrough 语义；不能原样应用于 EP0 对照组 |
| `flashinfer_moe_ep_mega_deep_gemm` | 不列为当前模型直接候选 | 虽接受 SM103，但适配器还要求 DeepseekV4 routing，不能仅因权重为 MXFP4 就用于 MiMo |
| `emulation` | 依赖满足后才可评估 | 需要 amd-quark；模拟路径，不代表原生 MXFP4 Tensor Core 性能 |
| `batched_triton`、`deep_gemm_mega_moe`、`cutlass`、`flashinfer_cutedsl`、`flashinfer_b12x`、`aiter_mega_moe`、`flydsl`、`hpc`、`rdna3` | 不是当前 MXFP4 路径的直接候选 | 通用 CLI 接受名称不等于当前模型选择器提供对应映射 |
| `b12x`、`aiter`、`aiter_triton_mxfp4_bf16`、`aiter_triton_mxfp4_mxfp4` | 其他架构/平台 | 不能因为 B300 也叫 Blackwell 就使用面向 SM12x 的 b12x |

参数名称说明：`FLASHINFER_TRTLLM_MXFP4_MXFP8` 是内部枚举；`flashinfer_trtllm_afp8` 仅见于内部映射，不在当前 CLI 的 MoEBackend 枚举中。要确认目标变体，必须检查实际后端日志及量化路径，不要使用未经 CLI 验证的别名。

当前 DP=2 也会影响专家实现选择：TRTLLM 的 Monolithic 实现要求 DP<=1；Modular 实现可接受更广泛的并行配置。因此不能把后端族名理解成唯一的底层 kernel。

## --attention-backend：Attention

| 参数值 / 设置 | B300 判断 | 说明 |
|---|---|---|
| 不指定 | 候选 | 模型自动选择 DiffKV；设备 major=10 且 FA4 可用时，版本选择默认倾向 FA4 |
| `FLASH_ATTN_DIFFKV` | 主要候选 | 适配当前 192/128 的 head dimension；结合 FA4，在当前源码的 10.x 分派路径预期使用 FlashAttentionForwardSm100 |
| `TRITON_ATTN_DIFFKV` | 对照候选 | 模型明确提供的 DiffKV 替代实现，需在 B300 上验证正确性和性能 |
| `FLASH_ATTN`、`TRITON_ATTN`、`FLASHINFER` 等普通后端 | 不能直接替换该 DiffKV 路径 | MiMo 对非 `_DIFFKV` 指定值仍可能重新自动选择 DiffKV |
| MLA、稀疏 MLA、其他模型专用后端 | 不适用当前模型路径 | 不是当前 MiMo DiffKV 的替代项 |
| `FlashAttentionForwardSm100` | 底层实现名称 | 不能作为 --attention-backend 参数值；名字含 Sm100 不意味着排除 SM103，当前源码对 10.x 家族分派至该实现 |

可用于 B300 验证的 vllm serve 参数片段：

```bash
--attention-backend FLASH_ATTN_DIFFKV \
--attention-config '{"flash_attn_version":4}'
```

这只指定后端与版本，最终实际 kernel 仍须由 trace 确认。FA3 是当前实现中的 SM90 路径；在 Blackwell 上指定 FA3 会触发回退逻辑，不能作为 B300 的独立 FA3 实验项。

## --all2all-backend：EP 通信

以下覆盖当前 All2AllBackend 枚举。所有依赖状态均需在 B300 目标机重新检测；本机 H20 上的 True/False 不代表 B300 环境。

| 参数值 | B300 判断 | 条件或限制 |
|---|---|---|
| `allgather_reducescatter` | 基线候选 | 标准集合通信路径；需要正常工作的多 GPU 通信环境 |
| `flashinfer_nvlink_one_sided` | 候选 | 需目标 GPU 组的 NVLink/NVSwitch、相应内存共享能力和 FlashInfer 接口；DeepGEMM FP4 明确不支持此组合 |
| `flashinfer_nvlink_two_sided` | 候选 | 同样需要目标拓扑和依赖验证；Marlin、DeepGEMM FP4 明确不支持此组合 |
| `flashinfer_all2allv` | 旧别名 | 等同 flashinfer_nvlink_two_sided，不作为独立变量 |
| `deepep_high_throughput` | 条件候选 | 安装兼容 B300 的 DeepEP，验证 NVLink/RDMA 与当前 MoE 组合 |
| `deepep_low_latency` | 条件候选 | 还需 RDMA、batched-experts 格式支持；不能假定普通专家实现均可搭配 |
| `deepep_v2` | 条件候选 | 需要 DeepEP v2 及其通信栈、拓扑和构建支持 |
| `moonep` | 条件候选，未验证 | 需要目标机依赖和模型接口验证 |
| `nixl_ep` | 条件候选，未验证 | 需要目标机 NIXL EP 依赖和通信环境验证 |
| `mori_high_throughput`、`mori_low_latency` | 不适用 | 当前实现面向相应 AMD GPU |
| `naive`、`pplx` | 已移除实现的兼容参数 | 回退到 allgather_reducescatter |
| `passthrough` | 特定融合 MoE 后端专用 | 后端内部完成通信时使用；不适用于普通 humming/marlin/TRTLLM 的单独通信对照 |

DeepEP 支持的硬件范围与各路径要求以其安装版本为准：[DeepEP 官方说明](https://github.com/deepseek-ai/DeepEP)。

## 可安排的对照范围与组合限制

| 实验目的 | 候选配置 | 验证重点 |
|---|---|---|
| 自动选择基线 | auto + FLASH_ATTN_DIFFKV + allgather_reducescatter | 记录最终 MoE 枚举、激活精度、FA 版本及实际 kernel |
| MoE 对照 | flashinfer_trtllm / deep_gemm / flashinfer_cutlass / marlin / humming | 固定 Attention 和通信；各后端可能改变激活精度，需同时比较输出质量 |
| Attention 对照 | FLASH_ATTN_DIFFKV（FA4） / TRITON_ATTN_DIFFKV | 固定已验证的 MoE 和通信；确认 trace 中的真实实现 |
| 通信对照 | allgather_reducescatter / 两种 flashinfer_nvlink 后端 | 先确认 MoE 组合兼容，再比较吞吐与通信耗时 |

明确限制：DeepGEMM FP4 不支持两种 FlashInfer NVLink 通信组合；Marlin 不支持 two-sided；带 batched-experts 要求的通信后端需要重新检查专家实现。不能将三列候选任意组合后视为全部可运行。
